# 01 · 架构设计

## 1. 分层总览

```
                         ┌───────────────────────────────┐
                         │            ui/                │
                         │  pages + widgets（只画界面）   │
                         └───────────────┬───────────────┘
                                         │ watch / read
                         ┌───────────────▼───────────────┐
                         │         providers/            │
                         │ Riverpod：装配 + 状态编排      │
                         └───┬───────────┬───────────┬───┘
                             │           │           │
              ┌──────────────▼──┐  ┌─────▼──────┐  ┌─▼──────────────┐
              │    domain/      │  │ services/  │  │     data/      │
              │ 纯业务逻辑       │  │ 系统能力    │  │ 数据库与 DAO    │
              │ 状态机 / 解析    │  │ 导入 / 录音 │  │ 模型 / 建表     │
              │ 吸附 / 循环数学  │  │ 通知 / 通道 │  │                │
              └─────────────────┘  └─────┬──────┘  └────────────────┘
                                        │ MethodChannel
                         ┌──────────────▼───────────────┐
                         │   Android 原生层（Kotlin）     │
                         │  SAF / MediaStore / 前台服务   │
                         └──────────────────────────────┘
```

依赖方向严格单向：`ui → providers → (domain | services | data)`，
`domain` 不依赖任何上层，`data` 不认识界面。

## 2. 各层职责与边界

### core（基础层）

与业务无关的通用能力，任何层都可以用。

| 文件 | 职责 |
| --- | --- |
| `constants/app_constants.dart` | 所有「魔法数字」的唯一出处：格式清单、倍速档位、吸附阈值、循环容差 |
| `errors/app_exception.dart` | `AppException` 及三个子类，外加 `humanizeError()` 统一转可读文案 |
| `theme/app_theme.dart` | `AppPalette`（ThemeExtension）承载亮暗两套配色，`AppDimens` 承载圆角与动效时长 |
| `utils/duration_utils.dart` | 时间格式化与倍速换算 |
| `utils/file_utils.dart` | 扩展名判断、体积格式化，纯函数便于单测 |

### data（数据层）

| 目录 | 内容 |
| --- | --- |
| `db/database_schema.dart` | 建表与建索引 SQL 集中一处，方便对照需求核查 |
| `db/database_helper.dart` | 开库、并发保护、外键开启。**不含任何业务 SQL** |
| `models/` | `MediaItem` / `SubtitleTrack` / `SubtitleLine` / `LoopPreset` / `AppSettings` |
| `dao/` | 每个表一个 DAO，只写 SQL，不写业务判断 |

设计取舍：模型自带 `toMap()` 与 `fromMap()`，不引入 codegen。
字段数量可控时手写映射更透明，也少一层构建步骤。

### domain（领域层）

**最干净的一层**，不引用 `data` 之外的任何东西，也不引用 Flutter 的 UI 库。
（唯一例外是 `LoopMode` 枚举放在 `data/models/media_item.dart`，被两侧共用。）

| 文件 | 职责 |
| --- | --- |
| `playback/playback_state.dart` | `PlaybackStatus` 状态枚举、`LoopRegion` 区间模型、`PlaybackSnapshot` 不可变快照 |
| `playback/playback_engine.dart` | 播放状态机本体，全应用唯一的播放状态源 |
| `playback/loop_math.dart` | 循环边界计算，抽成纯函数以便单测 |
| `playback/playable_source_resolver.dart` | 「URI 怎么变成播放内核能读的路径」的抽象，把平台差异隔离出去 |
| `subtitles/subtitle_parser.dart` | 三个解析器实现 + 注册表，按扩展名分发 |
| `subtitles/subtitle_text_utils.dart` | 三种格式共用的时间码解析与文本清洗 |
| `subtitles/subtitle_snapper.dart` | AB 边界吸附、当前句定位 |

### services（服务层）

需要系统能力或者需要跨层编排的地方。

| 文件 | 职责 |

| `recording_service.dart` | 录音与录音播放，只保留最新一条 |
| `background_playback_service.dart` | 通知栏内容同步与操作回调 |
| `app_directories.dart` | 私有目录管理（缩略图、录音） |
| `transcriber/` | AI 字幕识别抽象接口与注册表（见 03 号文档） |

## 3. 播放器状态机设计

这是整个项目的核心，需求第 9 条明确要求「播放器状态机逻辑集中管理」。
实现落在 `domain/playback/playback_engine.dart`，配套状态定义在同目录的 `playback_state.dart`。

### 3.1 状态定义

| 状态 | 含义 | 主按钮显示 |
| --- | --- | --- |
| `idle` | 还没打开任何媒体 | 播放 |
| `loading` | 正在打开或缓冲 | 播放 |
| `playing` | 播放中 | 暂停 |
| `paused` | 手动暂停 | 播放 |
| `gapCounting` | 跟读停顿倒计时中 | 暂停 |
| `loopFinished` | 指定遍数播完，停在片段末尾 | 播放（点一下再来一组） |
| `completed` | 播到文件末尾自动暂停 | 播放（点一下从头开始） |
| `error` | 出错，`errorMessage` 给出可读原因 | 播放 |

### 3.2 状态迁移图

```
                    open()
  idle ─────────────────────────▶ loading
                                    │
                          内核就绪  │
                                    ▼
                 ┌─────────────── playing ◀───────────────┐
                 │                  │                      │
        pause()  │                  │ 到达 B 点            │ _beginPass()
                 ▼                  ▼                      │（seek 到 A 再 play）
              paused          gapCounting ─────────────────┘
                 │                  │
                 │ play()           │ 指定遍数用尽
                 └──────▶ playing   ▼
                              loopFinished ──play()──▶ 重新开始这一组
                                     ▲
        播到文件末尾 ────────────────┴──▶ completed ──play()──▶ 从 0 开始

  任意状态 ──内核报错──▶ error
```

### 3.3 四个关键设计点

**（1）状态单向流动，引擎是唯一状态源**

引擎持有 `PlaybackSnapshot`，对外只暴露两类接口：

- 读：`stream Snapshots`（UI 通过 Riverpod 订阅）
- 写：`play()` / `pause()` / `seekTo()` / `setSpeed()` / `setLoopRegion()` ...

media_kit 暴露的十几个 stream（`position` / `playing` / `completed` / `error` ...）
在这里只作为**输入**：它们可以改变引擎的内部字段，但只有引擎的方法能推进状态。
这样就不会出现「内核说在播、界面显示暂停」这种两份状态打架的情况。

`playing` 流还有一层守卫：处理循环边界期间（`_handlingBoundary`）忽略它，
否则 `pause()` 触发的事件会把刚设好的 `gapCounting` 冲成 `paused`。

**（2）位置不信任内核回报，自己走一个高精度时钟**

这是 v1.0.1 修复的核心问题。用户反馈「AB 段反复跟读特别不精确」，
根因就在这里：一开始直接拿内核回报的播放位置判断有没有到 B 点，
但那个回调的间隔由解码器决定，音频上常常几十到几百毫秒才跳一次。
拿这种粗颗粒的位置去切句子，结果就是有的句子被切掉尾巴、有的多播一截。

现在由 [PlaybackClock] 自己走时钟：

| 机制 | 说明 |
| --- | --- |
| 锚点加真实时间推算 | 记下某时刻的音频位置与当时真实时间，之后用「真实经过时长 × 倍速」推进 |
| 内核只做校正 | 偏差在 120ms 内不动，超过才重锚，既平滑又不会飘走 |
| 缓冲时冻结 | 卡顿时音频没走，时钟必须一起停，否则会把「卡了 1 秒」算成「播了 1 秒」 |
| 变速先结算 | 换倍速前先把历史时间按旧倍速结算，否则旧时间会被新倍速错误换算 |

于是位置估算的粒度由调用方决定（现在是 20ms 轮询），完全摆脱了内核回调频率。

**（3）循环边界三层判定，容差方向永远是「多播」**

| 层次 | 周期 | 作用 |
| --- | --- | --- |
| 20ms 轮询 | 固定 | 精度的底座。位置一越过 `B + 30ms` 就处理，误差上限就是 20ms |
| 一次性精确计时器 | 按需排一次 | 省电优化。按算出来的剩余时长精准唤醒，省掉轮询空转 |
| 唤醒后复核 | 每次触发 | 保险。没到 B 就重排一小段继续等，绝不在没播完时提前切 |

容差方向定在 `B + 30ms`：宁可多播几十毫秒，也不能把句子尾巴吃掉。
暂停本身还有十几毫秒延迟，正好抵消。

**（4）只在区间内才生效，且改动立刻可见**

两个规则配套使用：

- `_loopSuppressed`：用户主动跳到 B 点之后（例如点字幕列表的下一句），
  循环暂时失效，否则一跨进区间就被旧选区拽回 A 点，体验很糟。
  跳回区间内或用 `startLoop()` 会重新激活。
- `setLoopRegion` 立刻生效：播放中调 A/B 时，如果当前位置落在新区间外
  （缩短片段、或把 A 往后挪），马上回到 A 重新开始，
  而不是等播放自然走到 B 才起作用。这一条直接解决用户说的「改了 AB 不立即生效」。

### 3.4 跟读停顿的防串台

停顿倒计时是异步的（`Timer.periodic` 每秒一跳，倒计时结束后自动开下一遍）。
如果用户在中途按了暂停，倒计时结束时代码不应该自作主张继续播。

解决办法是一个代次号 `_gapGeneration`：

```dart
final generation = ++_gapGeneration;
await completer.future;                      // 等倒计时结束或被取消
if (generation != _gapGeneration) return;    // 代次变了说明被打断，直接返回
await _beginPass();
```

`pause()` / 清选区 / 切文件都会 `_gapGeneration++`，
于是「倒计时结束后偷偷继续播」这条路径被彻底堵死。

### 3.5 循环结束行为

需求原文：「循环完设定遍数后**自动暂停并停在片段末尾**，等待用户操作，不自动继续往下播放」。

实现是：`pause()` 之后 `seek(region.endMs)`，状态置为 `loopFinished`，然后就停在那里。
界面上的循环按钮此时显示「再来一组」，用户按播放键会重新从头跑这一组循环，
想正常往下播就按「清除」退出循环模式。

## 4. 原生层设计

原生层刻意做窄，只解决 Flutter 不好做的四件事。

### 4.1 文件访问：为什么不复制文件

需求的硬性要求是「只记录 URI 引用，不复制、不移动用户原始文件」。
这一点决定了导入方式：

| 方式 | 结果 | 是否复制 |
| --- | --- | --- |
| `file_picker` 之类插件 | 返回一个缓存目录里的副本 | 复制，不符合要求 |
| SAF（`ACTION_OPEN_DOCUMENT`） | 返回 `content://` URI，可申请持久化读权限 | 不复制 |
| MediaStore 查询 | 返回 `content://media/...` URI | 不复制 |

所以两条路线都用原生实现，绕开了插件默认的复制行为。

### 4.2 URI 怎么变成能播的路径

mpv 不认 `content://`，必须给真实路径。按代价从低到高尝试：

1. **真实文件路径**。MediaStore 索引里的媒体可以通过 `DATA` 列拿到
   `/storage/emulated/0/Movies/x.mp4`，配合 `READ_MEDIA_*` 权限可直接读。
2. **文件描述符路径**。SAF 选中的文件不在 MediaStore 索引里，
   这时打开 `ParcelFileDescriptor` 并暴露成 `/proc/self/fd/N`。
   对 mpv 来说这就是个普通文件，可读可 seek。
   代价是必须持有这个 fd 直到播放结束，所以原生侧用 Map 缓存，
   Flutter 侧切换媒体时显式释放。

这两条路分别对应 `PlaybackPathResolver.kt` 里的两个分支。

### 4.3 前台服务为什么不做播放

`PlaybackService.kt` 里**没有任何解码逻辑**，它只做两件事：

1. 用前台服务加上通知，把进程优先级抬到用户可感知，避免锁屏后被系统回收
2. 承载锁屏与通知栏的按钮，把动作通过回调传回 Flutter

这样播放状态的源头始终只有 Flutter 侧那一个引擎。
如果改成 `audio_service` 那套方案，播放器会被包一层代理，
状态就要在两边同步，容易出现「通知栏显示暂停但实际在播」这类问题。

### 4.4 模块划分

| 文件 | 职责 |
| --- | --- |
| `MainActivity.kt` | 承载 Flutter 界面，转发 Activity 结果与权限结果 |
| `NativeBridge.kt` | 通道分发中枢，把语义化方法名映射到具体能力 |
| `MediaImporter.kt` | 读取媒体元数据（名称、体积、MIME、时长） |
| `PlaybackPathResolver.kt` | URI 到可播路径的解析与 fd 生命周期管理 |
| `ThumbnailHelper.kt` | 抽首帧并压缩成 JPEG |
| `RecorderHelper.kt` | MediaRecorder 录音 |
| `PlaybackService.kt` | 前台服务与媒体通知 |

## 5. 数据流：一次完整的「导入到循环」

```
用户点「导入文件」
  → ui/library_page 调 library_provider.importFromPicker()
  → media_import_service 调 native_channel.pickMediaFiles()
  → NativeBridge 拉起 SAF，拿回 content:// URI 并申请持久化权限
  → MediaImporter 读出名称 / 体积 / 时长
  → 按 URI 去重后写 media 表
  → thumbnail_service 抽首帧存到私有目录，路径回写 media 表
  → library_provider.refresh() 重新查列表
  → 界面刷新卡片

用户进入播放页
  → player_page 读 media 表拿到条目
  → subtitle_provider.loadFor(mediaId) 读激活轨的字幕句
  → playback_provider.openMedia(item)
      · 把该文件上次存的循环区间、播放位置、全局倍速一起交给引擎
      · 引擎调 resolver.resolve(uri)，原生把 URI 换成可播路径
      · 引擎 open 之后按需 seek 到上次位置并 play
  → background_playback_service 拉起前台服务，通知栏出现播放控制

用户框选并循环
  → timeline_bar 拖动时若开启吸附，调 subtitle_provider.snap()
      → subtitle_snapper 找 1 秒内最近的字幕边界
  → 松手后 playback_provider.setLoopRegion(start, end)
      · 引擎更新 snapshot 并排下精确计时器
      · 同时把区间写回 media 表（单文件独立存储）
  → 播放到 B 点触发 _onLoopBoundary()
      · 有停顿 → gapCounting，通知栏文案变成「跟读中 3…」
      · 无停顿 → seek 到 A 继续
      · 遍数用尽 → loopFinished，停在 B
```
